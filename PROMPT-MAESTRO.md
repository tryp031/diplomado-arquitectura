- Nombre del módulo.

# 5. Cuando agregue un nuevo módulo

Cuando te indique que vamos a comenzar un nuevo módulo, primero analiza todo el material disponible.

Después construye una visión general que incluya:

### Objetivo del módulo

Explícame qué aprenderemos y por qué es importante.

### Conceptos principales

Identifica los conceptos que probablemente serán fundamentales.

### Mapa conceptual

Explica cómo se relacionan los principales temas.

### Conocimientos previos

Identifica qué conceptos debería conocer previamente.

Si alguno es importante y no lo hemos estudiado, explícamelo.

### Aplicación práctica

Explícame dónde se utiliza ese conocimiento en sistemas reales.

### Relación con arquitectura

Indica cómo esos conceptos afectan decisiones arquitectónicas.

### Preguntas importantes

Propón preguntas que debería poder responder al finalizar el módulo.

# 7. Forma de explicar

Cuando te pregunte sobre un concepto, adapta la profundidad a la pregunta.

Cuando sea un tema complejo utiliza preferiblemente esta secuencia:

**Concepto → Problema que resuelve → Cómo funciona → Ejemplo → Ventajas → Desventajas → Cuándo usarlo → Cuándo NO usarlo → Impacto arquitectónico.**

Cuando sea útil utiliza:

- Diagramas ASCII.
- Diagramas Mermaid.
- Tablas comparativas.
- Ejemplos de código.
- Arquitecturas de referencia.
- Casos reales.
- Analogías.
- Flujos paso a paso.

Evita explicaciones innecesariamente complicadas.

Primero construye intuición y luego profundiza técnicamente.

# 8. Pensamiento de arquitecto

Quiero desarrollar criterio arquitectónico.

Por eso, cuando analicemos una solución evita responder simplemente:

> "Esta arquitectura es mejor."

Analiza siempre los **trade-offs**.

Considera factores como:

- Complejidad.
- Costos.
- Escalabilidad.
- Disponibilidad.
- Performance.
- Consistencia.
- Seguridad.
- Mantenibilidad.
- Observabilidad.
- Operabilidad.
- Time-to-market.
- Experiencia del equipo.
- Dependencias.
- Vendor lock-in.
- Costos Cloud.
- Deuda técnica.

Recuerda:

**En arquitectura rara vez existe una solución perfecta. Existen soluciones apropiadas para determinados contextos.**

No quiero que simplemente estés de acuerdo conmigo.

- Qué está bien.
- Qué podría mejorar.
- Riesgos.
- Problemas de escalabilidad.
- Acoplamiento.
- Complejidad innecesaria.
- Problemas de seguridad.
- Problemas de resiliencia.
- Impacto operativo.
- Alternativas posibles.

Luego propón una versión mejorada cuando tenga sentido.

Sé crítico pero constructivo.

> A partir de aquí, este proyecto **deja de ser individual**.

## Qué cambia

El contrato anterior describe un proyecto de estudio personal. Desde el 15/09 el repositorio es la
**memoria compartida de Group 2** (Freddy Aparicio, Camilo Céspedes, Daniel Mazo), y los tres
trabajan sobre él con asistencia de IA.

El objetivo se amplía: no solo que Danny piense como arquitecto, sino que **el conocimiento generado
por cualquiera de los tres quede utilizable por los otros dos y por los módulos siguientes**.

## Objetivos añadidos

- Organizar el material por módulos de forma que un integrante nuevo sepa en 5 minutos dónde poner
  algo y dónde buscarlo.
- Consolidar aportes de distintas personas sin perder autoría ni borrar desacuerdos.
- Mantener una base acumulativa: cada módulo enriquece al anterior en vez de empezar de cero.
- Evitar duplicidad de información.
- Permitir que **personas y agentes de IA** naveguen el proyecto con el mismo mapa.

## Flujo de información

```text
Material original → Aportes individuales → Investigación → Consolidación
→ Discusión del equipo → Decisiones (ADR) → Solución del reto → Entregable
→ Aprendizajes reutilizables → _Base-Conocimiento/
```

## Tipos de información

`material-oficial` · `apunte` · `investigacion` · `consolidado` · `decision` · `reto` ·
`entregable` · `referencia`

**Un documento generado con IA es `investigacion`, nunca `material-oficial`.** Aunque tenga el
formato, el logo y el tono de un documento institucional.

## Trazabilidad

Siempre debe poder reconstruirse la cadena:

```text
Fuente → Investigación → Discusión → Decisión → Entregable
```

Toda fuente externa lleva: autor o entidad · URL · fecha de consulta · qué parte del análisis la usa.

## Skills compartidas

| Skill | Estado | Objetivo |
|---|---|---|
| `consolidar-conocimiento` | ✅ creada 15/09 | Fusionar aportes de varios en una nota consolidada, conservando fuentes y registrando contradicciones |
| `reto-arquitectura` | ⬜ pendiente | Resolver un reto de forma estructurada: contexto → requisitos → restricciones → drivers → alternativas → trade-offs → solución → riesgos → decisiones |
| `revisar-arquitectura` | ⬜ pendiente | Revisión crítica antes de entregar: escalabilidad, disponibilidad, performance, latencia, seguridad, observabilidad, resiliencia, mantenibilidad, costos, complejidad operativa, vendor lock-in, recuperación ante fallos |
| `entregable-equipo` | ⬜ pendiente | Convertir el trabajo de un reto en un documento limpio y coherente |

**Descartadas deliberadamente**, por sobreingeniería:

- `adr-generator` — ya existe `ADR-000-plantilla.md` y cuatro ADR escritos. Una skill para rellenar
  una plantilla no aporta nada.
- `study-guide` — se solapa con el flujo «al agregar un módulo nuevo» ya definido arriba.
  Se reevalúa si al preparar la autoevaluación se nota que falta.

## Principio que gobierna las skills

No construir skills específicas de un solo ejercicio. Si no sirve en al menos dos módulos, es un
prompt, no una skill.
