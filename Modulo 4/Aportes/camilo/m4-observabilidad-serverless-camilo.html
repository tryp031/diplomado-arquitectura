1 · Qué investigué y por qué

El taller despliega una API sencilla de “ítems” sobre servicios serverless de AWS y la usa para aprender a observarla: medir su comportamiento (métricas), registrar lo que ocurre (logs) y seguir el recorrido de cada petición entre servicios (trazas). La aplicación es pequeña a propósito; lo valioso es la instrumentación que se construye a su alrededor.

  • Métricas propias (de negocio y de ciclo de vida) en CloudWatch, publicadas de forma síncrona y asíncrona.
  • Logs estructurados y access logs de API Gateway, consultables con CloudWatch Logs Insights.
  • Trazas distribuidas con AWS X-Ray: subsegmentos, anotaciones y metadata.

Todo se despliega con AWS SAM en la región us-east-2 (Ohio). Documento redactado para dejar constancia de qué cubre el despliegue y de cómo reproducirlo.

4 · Preparación del entorno

Credenciales de AWS

  1. En IAM, crear una access key para el usuario con el caso de uso Local code y descargar el CSV (la clave secreta solo se muestra una vez).
  2. Registrarla como perfil local (por ejemplo develop) desde la extensión AWS Toolkit de VS Code (opción IAM credentials) o con aws configure --profile develop. Queda en ~/.aws/credentials.
  3. Dar al usuario permisos para Lambda, DynamoDB, S3, CloudWatch, API Gateway, IAM y SNS.

Seguridad: la access key no se comparte ni se sube al repositorio. En el taller se usaron permisos amplios por simplicidad; en un entorno real conviene mínimo privilegio y desactivar la clave al terminar. Recomendación

Herramientas

  • Node.js 20, AWS CLI y AWS SAM CLI. Docker en ejecución.
  • Git y un cliente HTTP (Postman o PowerShell).
  • En Windows, si PowerShell bloquea npm por la política de ejecución de scripts, se usa npm.cmd o Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned.

Ajuste al template

El template original usa el runtime nodejs18.x; el video indica cambiarlo a nodejs20.x en Globals → Function. Curso

6 · Pruebas de la API

Invoke-RestMethod -Method Post -Uri "$api/items" -ContentType "application/json" -Body '{"id":"1","name":"Item uno"}'
Invoke-RestMethod -Method Post -Uri "$api/items" -ContentType "application/json" -Body '{"id":"2","name":"Item dos"}'
Invoke-RestMethod -Uri "$api/items"
Invoke-RestMethod -Uri "$api/items/1"

Verificado Los POST responden 200 con cuerpo vacío, GET /items devuelve los ítems con su conteo y GET /items/1 devuelve el ítem pedido. Un método no definido en la API (por ejemplo PATCH) lo rechaza API Gateway con 403, antes de llegar a la Lambda Curso.

7 · Métricas

Métricas personalizadas en el namespace MonitoringApp, con dos estrategias:

Síncronas (putMetric)Asíncronas (EMF)
Cómo funcionanLa Lambda llama a la API de CloudWatch durante su ejecución.La Lambda escribe una línea JSON en su log (Embedded Metric Format) y CloudWatch extrae la métrica.
Dónde se aplicóput-itemget-all-items y get-by-id
VentajaSencillas de entender; la métrica sale directamente.No bloquean ni dependen de la disponibilidad del servicio de métricas.
RiesgoSi CloudWatch falla o tarda, puede afectar la operación de negocio.Requiere AWS_EMF_NAMESPACE y entender las dimensiones que agrega la librería.

Métricas definidas

  • ColdStart: una vez cuando el contenedor de la función se inicializa.
  • SuccessfulPutItem / FailedPutItem, SuccessfulGetAllItems / FailedGetAllItems, SuccessfulGetItem / FailedGetItem: éxitos y fallos por operación.
  • UnsupportedHTTPMethod: llamada con un método no permitido.

Qué se verificó en CloudWatch

  • Verificado Síncronas: ColdStart = 1 y SuccessfulPutItem = 2 tras dos POST.
  • Verificado EMF: SuccessfulGetAllItems y SuccessfulGetItem visibles; con estadística Sum y periodo de 5 minutos, el segundo llegó a 5 tras varias consultas.
  • No verificado Las métricas de fallo y UnsupportedHTTPMethod: API Gateway bloquea los métodos no definidos, así que desde la API no se pueden provocar.

Hallazgo propio: las métricas EMF aparecen bajo otro grupo de dimensiones (LogGroup, ServiceName, ServiceType, operation) que las síncronas (operation, service), porque la librería agrega dimensiones por defecto. Además, para contar eventos hay que usar la estadística Sum: con Average, cada dato vale 1 y el resultado siempre es 1. Complementario

Las métricas de negocio sirven para alarmas (por ejemplo, avisar por correo vía SNS cuando SuccessfulGetAllItems supere un umbral) y para dashboards de negocio y operación. Curso

8 · Logs

El módulo de logs busca centralizar el registro de la aplicación y poder analizarlo, no solo guardarlo. Curso

  • API Gateway: access logs en JSON (con requestId, método, ruta, estado, xrayTraceId…). Requiere un rol IAM con la política AmazonAPIGatewayPushToCloudWatchLogs y un recurso AWS::ApiGateway::Account que lo asocie.
  • Lambdas: un logger estructurado que registra el evento, el contexto, el detalle de cada operación y el resultado, con un campo operation y el identificador de traza.
  • CloudWatch Logs Insights: consultas como filter @message like /operation/ y stats count(*) by operation permiten agregar y contar peticiones; el resultado se puede añadir como widget de tabla a un dashboard.

Preparado Los cambios de código y de template para esta parte están escritos en sample-app, tomando code/backend como referencia. Las consultas en Logs Insights no se ejecutaron en esta sesión.

La diferencia con las métricas: las métricas dan el total de forma barata y rápida; los logs permiten desglosar por cualquier campo (por ejemplo, por categoría de producto) y enriquecer los dashboards de negocio. Curso

9 · Trazas con AWS X-Ray

Las trazas muestran el camino de cada petición entre componentes y cuánto tarda cada tramo, lo que ayuda a encontrar cuellos de botella.

Cambios aplicados

  • En el template: Tracing: Active para todas las funciones y TracingEnabled: true en la API.
  • En el código: aws-xray-sdk-core con captureAWS (antes de crear los clientes de DynamoDB y SNS), subsegmentos por operación (## Handler, ## putItemData, ## publishNewItemSNS…), anotaciones (Status, ItemID, ItemsCount) y metadata con el payload enviado a DynamoDB y SNS.

Qué se observó

  • Verificado El Trace Map mostró el recorrido completo: cliente → API Gateway → Lambdas → DynamoDB, y la ruta put-item → SNS → notify-item.
  • Verificado La lista de trazas devolvió peticiones con estado OK y código 200, con tiempos de respuesta de unos 2,3 a 2,8 s y 3,5 s de duración para el POST. Se explica por el cold start de la primera ejecución más la publicación en SNS.
  • No verificado El contenido de anotaciones y metadata de una traza concreta no se inspeccionó en esta sesión; están definidas en el código.

Las anotaciones se indexan y permiten filtrar trazas, por ejemplo con annotation.Status = "SUCCESS"; la metadata no se indexa y sirve para ver el detalle de lo enviado a cada servicio. Complementario

  • Módulo 2 (Reto 2, opción B en AWS): el diseño API Gateway → Lambda → SQS → Lambda ya se midió con CloudWatch Logs Insights (medir-aws.py). Aquí se profundiza en cómo se generan esas métricas y logs desde el código.
  • Infraestructura reproducible: la opción B del M2 se armó en la consola de AWS y no se podía reproducir desde el repo (queda abierto el pedido de exportarla o pasarla a IaC). En este módulo, SAM sí describe todo en un template.
  • Módulo 3 (resiliencia): las métricas de éxito y fallo, las alarmas y las trazas son la base para medir degradación y recuperación de un servicio. Recomendación
  • Atributos de calidad: la observabilidad habilita medir disponibilidad, desempeño y confiabilidad de forma continua. Recomendación

12 · Hallazgos y contradicciones

Cosas que encontré y que no coinciden con lo esperado. No se resuelven aquí: se registran.

HallazgoDetalle
README vs. estructura realEl README menciona sample-app y sample-app-tracing, pero no documenta backend/ ni cloudwatch-cdk/, y enlaza una imagen /img/architecture.png.
Mensaje SNS con datos fijosEn put-item el mensaje publica id: 1 y name: "N/A" fijos (las líneas con los datos reales están comentadas), así que notify-item siempre recibe lo mismo.
Mensaje de log engañosoEn backend/put-item.js, el log de método inválido dice “only accept GET” cuando el método válido es POST.
Dependencias sin soporteAWS SDK v2, Jest 26 y CDK v1. Por eso el despliegue de dashboards con cloudwatch-cdk falla, y el video termina creándolos a mano.
Runtime Node.jsEl template trae nodejs18.x (ya obsoleto); el video pide nodejs20.x, que a su vez ya figura como deprecado, aunque aún permite crear y actualizar.
X-Ray en la APIEn el video el tracing del stage de API Gateway se activa a mano tras el despliegue; en nuestro template va declarado con TracingEnabled: true.

13 · Problemas y lecciones

SituaciónCausa y solución
npm bloqueado en PowerShellLa política de ejecución impide los scripts .ps1. Se usa npm.cmd o se ajusta la política solo para el usuario actual.
Security Constraints Not Satisfied en sam deploy -gSe respondió n a la pregunta de funciones sin autenticación. Hay que aceptar y para cada función con API pública (es una demo).
Despliegue fallido por permisosEl usuario necesita permisos adicionales (API Gateway, IAM, SNS). Un stack que falla queda en ROLLBACK_COMPLETE y debe eliminarse antes de reintentar.
Las métricas EMF “no aparecen”Estaban bajo otro grupo de dimensiones. Se buscó en Browse el grupo con LogGroup, ServiceName, ServiceType.
Contadores siempre en 1Estadística Average. Se cambió a Sum.
Gráfico o mapa vacíoLa ventana de tiempo no incluía los datos o aún no se generaba tráfico. Se amplió el rango y se esperó el periodo de 5 minutos.

16 · Limpieza y costos

Los recursos siguen activos mientras existan los stacks. Para eliminar todo lo desplegado con SAM:

cd code/sample-app
sam delete --profile develop

cd ../sample-app-tracing
sam delete --profile develop

Lo creado a mano en la consola (alarmas, tópicos SNS de alarmas, dashboards) no lo elimina SAM y se borra aparte. Al terminar el curso conviene desactivar la access key y retirar los permisos amplios.

Idea central: la observabilidad no es solo vigilar infraestructura. Con métricas de negocio, logs analizables y trazas se detectan problemas, se optimizan tiempos (y, en serverless, costos) y se decide con datos. Conviene aplicarla con criterio, priorizando los procesos críticos.
