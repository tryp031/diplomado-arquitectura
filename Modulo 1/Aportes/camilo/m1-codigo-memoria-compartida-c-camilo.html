1. Visión general

Memoria compartida C son dos programas en C que se ejecutan a la vez: un servidor que clasifica hosts y un cliente que le envía estímulos y cronometra cada respuesta. No se envían mensajes por una red ni por un socket: ambos programas leen y escriben una misma zona de memoria y se avisan mutuamente cambiando un contador. Todo el código cabe en unas 890 líneas, repartidas así:

Qué pasa en una corrida completa (--out)

  1. El servidor arranca. Carga la tabla de hosts, crea la región de memoria compartida (con nombre /latm-D-9103), la deja a cero y queda girando, esperando que el contador de petición cambie.
  2. El cliente arranca. Carga la misma tabla, abre la región (reintenta hasta 50 veces cada 50 ms, por si el servidor todavía no la creó) y prepara 16 estímulos.
  3. Autoprueba. Antes de medir, el cliente envía los 16 hosts de la tabla y uno desconocido y comprueba que los veredictos sean los esperados.
  4. Warmup. Ejecuta cien mil intercambios que no se guardan, para que cachés y frecuencia de CPU se estabilicen.
  5. Medición. Para cada intercambio anota el instante antes y después, y guarda la diferencia.
  6. Contraste por lotes. Repite el intercambio en bloques de 1000 y mide cada bloque completo, como comprobación cruzada.
  7. CSV. El cliente escribe todas las latencias en un archivo y termina.
  8. El servidor se detiene cuando recibe una señal de terminación: libera la región y sale.

Esta es la corrida oficial (la que usan run.sh y el botón «Medir rendimiento» de la web). El cliente tiene además una segunda forma de arrancar, mucho más corta — un estímulo suelto con --clasificar, sin CSV ni autoprueba — que usa el botón «Probar clasificación» de la web. Es una rama completamente aparte del programa: se explica en la sección 6.

2. common.h — la región compartida

Es el archivo más corto y el más importante: define qué se comparte. Todo lo demás (servidor y cliente) es código que lee y escribe esta estructura.

#define LINEA_CACHE 128
#define PAYLOAD_MAX (LINEA_CACHE - sizeof(uint64_t))   /* 120 B */

typedef struct {
    _Alignas(LINEA_CACHE) _Atomic uint64_t seq;        /* contador de secuencia */
    unsigned char dato[LINEA_CACHE - sizeof(uint64_t)];/* el mensaje */
} ranura_t;

typedef struct {
    ranura_t peticion;    /* cliente escribe, servidor lee */
    ranura_t respuesta;   /* servidor escribe, cliente lee */
} region_t;

Cómo leer esta estructura

  • _Atomic uint64_t seq es un número de 64 bits que se lee y se escribe de forma indivisible: nadie puede verlo a medias. Es el «timbre»: quien escribe un mensaje sube el número, y quien espera detecta que cambió.
  • dato[120] es el mensaje. Se usan 32 bytes por defecto; el resto queda libre.
  • _Alignas(128) hace que cada ranura empiece en una dirección múltiplo de 128. Así peticion y respuesta quedan en líneas de caché distintas. Si compartieran línea, cada escritura de un proceso obligaría al otro núcleo a descartar su copia (false sharing) y la latencia aumentaría mucho.
  • Cada ranura tiene un solo escritor. El cliente solo escribe en peticion y el servidor solo en respuesta, por eso no hace falta ningún cerrojo.
  • El contador y el mensaje comparten línea: cuando el otro núcleo ve el contador nuevo, el mensaje ya viajó con él en la misma transferencia.

3. reloj.h — el reloj y la pausa

Contiene las dos herramientas de bajo nivel que necesitan ambos programas: leer la hora en nanosegundos y esperar sin ceder la CPU.

LíneasQué hace
1–22Comentario: por qué se usa este reloj. La tabla de granularidades medidas (1000 ns para CLOCK_MONOTONIC en el equipo de referencia frente a 41 ns de CLOCK_UPTIME_RAW) justifica la elección.
33–42ahora_ns(): devuelve la hora actual en nanosegundos, de un reloj que nunca retrocede. En macOS usa clock_gettime_nsec_np(CLOCK_UPTIME_RAW); en el resto, clock_gettime(CLOCK_MONOTONIC). Es lo que se usa para cronometrar.
44–57pausa_spin(): la pausa que se inserta dentro de los bucles de espera activa. En arm64 emite isb sy; en x86-64, pause (__builtin_ia32_pause); en otras arquitecturas, una barrera vacía. No cede el núcleo al sistema operativo: solo indica a la CPU que está girando, lo que ahorra energía y mejora la espera.
59–63latm_cmp_u64: función de comparación de enteros de 64 bits, para ordenar con qsort.
65–98reloj_verificar(): mide la granularidad real del reloj (el menor salto no nulo entre dos lecturas seguidas) y el costo de un par de lecturas, sobre 100 000 pares.
100–107reloj_avisar_si_grueso(): avisa si la granularidad no es al menos diez veces menor que la latencia esperada.

El servidor y el cliente de Memoria compartida C usan ahora_ns() y pausa_spin(). Las funciones reloj_verificar() y reloj_avisar_si_grueso() no se invocan desde este cliente, que mide por su cuenta el costo del reloj (sección 6, «Piso de medición»).

4. clasificador.h — el dominio

Define qué significan los mensajes: dado un host, ¿es local, externo o desconocido? Contiene la tabla de hosts, la función que clasifica, el cargador del archivo CSV y el formato de los mensajes. Lo comparten las dos variantes.

LíneasQué hace

clasificar(): la función que se ejecuta en cada mensaje

static inline uint8_t clasificar(uint32_t id)
{
    uint8_t v = (uint8_t)VEREDICTO_DESCONOCIDO;
    for (int i = 0; i < TABLA_MAX; i++)
        v = (g_tabla_id[i] == id) ? g_tabla_ver[i] : v;
    return v;
}
  • Parte de «desconocido» y compara el identificador con las 16 entradas, siempre. Si alguna coincide, toma su veredicto.
  • No hay salida anticipada ni if dependiente del dato: el ? : se traduce a una instrucción de selección condicional (csel en arm64, cmov en x86). Por eso clasificar un host local, uno externo o uno desconocido cuesta lo mismo, y la latencia no depende de qué host se consulte.
  • Si hubiera direcciones repetidas en la tabla, ganaría la última, porque el recorrido nunca se detiene.

clasificador_cargar(): cómo se lee la tabla

  1. Pone las 16 ranuras en «libre» con veredicto «desconocido» (líneas 107–111).
  2. Abre el archivo; si no puede, informa el error y devuelve −1 (113–118).
  3. Lee línea por línea (hasta 256 caracteres). Salta los comentarios (que empiezan con #) y las líneas vacías (122).
  4. Separa cada línea en tres campos nombre,ip,veredicto con sscanf (125). Una línea que no tenga los tres campos se ignora en silencio. La fila de cabecera (nombre) también se salta (126).
  5. Si ya hay 16 y aparece otra, aborta con un mensaje: el límite es una decisión de diseño (128–134).
  6. Convierte la IP con inet_pton; si no es válida, aborta (136–141). El resultado se guarda tal cual, en orden de red, sin convertir el orden de bytes (152).
  7. Interpreta el veredicto: local → 1, externo → 0; cualquier otra palabra aborta (143–150).
  8. Si al final no hay ninguna entrada, informa el error; si no, devuelve cuántas cargó (158–162).

Cómo se crea la región (líneas 92–106)

  1. Construye el nombre con el puerto: /latm-D-9103.
  2. shm_unlink(nombre): borra cualquier región anterior con ese nombre, por si quedó una de una ejecución que terminó mal.
  3. shm_open(..., O_CREAT | O_EXCL | O_RDWR, 0600): crea el objeto nuevo. O_EXCL falla si ya existe; 0600 deja el permiso solo al usuario.
  4. ftruncate: le da el tamaño de region_t (256 bytes).
  5. mmap(..., MAP_SHARED, ...): lo proyecta en la memoria del proceso; el resultado r es un puntero a la región. Como es MAP_SHARED, lo que un proceso escribe lo ve el otro. Después se cierra el descriptor, que ya no hace falta.
  6. memset a cero y los dos contadores seq en 0.

La ruta caliente (líneas 119–148)

uint64_t ultima = 0;

while (!g_salir) {
    uint64_t s;
    /* espera activa: gira hasta que el contador de petición cambie */
    while ((s = atomic_load_explicit(&r->peticion.seq, memory_order_acquire)) == ultima) {
        if (g_salir) goto fin;
        pausa_spin();
    }
    ultima = s;

    memcpy(recibido, r->peticion.dato, payload);            /* leer el estímulo */

    uint32_t host_id;
    memcpy(&host_id, recibido + OFF_HOST_ID, sizeof host_id);
    respuesta[OFF_VEREDICTO] = sin_clasificar ? (uint8_t)VEREDICTO_LOCAL
                                              : clasificar(host_id);
    memcpy(respuesta + OFF_ECO_ID, &host_id, sizeof host_id);

    memcpy(r->respuesta.dato, respuesta, payload);          /* escribir la respuesta */
    atomic_store_explicit(&r->respuesta.seq, s, memory_order_release);
}
  • Esperar. El bucle interno lee peticion.seq una y otra vez. ultima guarda el último valor atendido; mientras el contador siga igual, no hay petición nueva. Cada vuelta llama a pausa_spin() y revisa si llegó una señal de terminación. Esta espera consume un núcleo completo.
  • memory_order_acquire garantiza que, si el servidor ve el contador nuevo, también ve el mensaje que el cliente escribió antes de subirlo.
  • Leer y responder. Copia el estímulo a un buffer local, extrae el host, calcula el veredicto y escribe la respuesta en el buffer local: el veredicto en el byte 0 y el eco del host en los bytes 4–7. Los demás bytes quedan en cero.
  • Publicar. Copia la respuesta a la ranura compartida y, después, escribe el contador con memory_order_release. El orden importa: el contador es la señal de «respuesta lista», y release asegura que el cliente que lo vea también vea la respuesta completa.
  • La respuesta lleva como seq el mismo valor que la petición, y así el cliente sabe a cuál corresponde.

Nótese que el servidor no distingue una corrida completa de un estímulo suelto: siempre es el mismo bucle, atendiendo una petición a la vez. La diferencia entre los dos modos vive enteramente en el cliente (sección 6).

El modo estímulo suelto: --clasificar (líneas 178–215)

Esta variante no tiene sockets que aceptar: cliente y servidor comparten memoria, no una conexión de red. Para que el plano de control pueda mandarle una pregunta suelta sin levantar todo un cliente medidor residente, lanza este mismo binario una vez por pregunta, con --clasificar <ip>.

if (clasificar) {
    unsigned char est[PAYLOAD_MAX];
    uint32_t hid = id_de_ip(clasificar);
    armar_estimulo(est, payload, hid, 0);

    uint64_t t0 = ahora_ns();
    INTERCAMBIO(est);
    uint64_t t1 = ahora_ns();

    uint32_t eco;
    memcpy(&eco, recibido + OFF_ECO_ID, sizeof eco);
    if (eco != hid) { /* ... error ... */ }
    if (giros_perdidos) { /* ... error ... */ }

    printf("ESTIMULO veredicto=%u latencia_ns=%llu\n",
           (unsigned)recibido[OFF_VEREDICTO], (unsigned long long)(t1 - t0));
    return 0;
}
  • Es la misma macro INTERCAMBIO de siempre, con un solo estímulo en vez de un ciclo de 16. No hay un camino de código nuevo para «hablar» con el servidor: es literalmente un intercambio suelto, con la misma frontera F1 (t0 antes, t1 después) que usa la medición oficial.
  • No toca el bucle medido ni la autoprueba — es una rama que hace return 0 antes de llegar a ellas. Ninguna cifra del informe depende de este código: es, literalmente, lo que dice el comentario del propio archivo.
  • La salida es un contrato, no un mensaje para humanos: la línea ESTIMULO veredicto=<n> latencia_ns=<n> es la única que el plano de control sabe leer — la busca con l.startswith("ESTIMULO ") en estimulo_por_cliente(), en app/servidor.py. Cualquier otra línea en stdout es ruido para ese consumidor (aunque puede servir a un humano leyendo la consola directamente).
  • El servidor se niega a compartirse. Del lado de app/servidor.py: si hay una medición en curso, el plano de control ni siquiera llega a lanzar este proceso — lo rechaza antes, porque la región tiene una sola ranura por sentido y un cliente de estímulo suelto correlacionaría con el que está midiendo (payload cruzado, corrida contaminada sin error visible).
  • El precio es el arranque del proceso (milisegundos): no entra en la cifra que se reporta, porque t0/t1 rodean solo el intercambio, no el arranque del cliente. Por eso la interfaz muestra el estímulo suelto con una nota: sirve para ver que clasifica, no para comparar con el p50 de una corrida de un millón.

La macro INTERCAMBIO: el protocolo completo del cliente

#define INTERCAMBIO(EST)                                                          \
    do {                                                                          \
        memcpy(r->peticion.dato, (EST), payload);                                 \
        atomic_store_explicit(&r->peticion.seq, ++n, memory_order_release);       \
        uint64_t giros = 0;                                                       \
        while (atomic_load_explicit(&r->respuesta.seq, memory_order_acquire) != n) { \
            if (++giros > LIMITE_SPIN) { giros_perdidos++; break; }               \
            pausa_spin();                                                         \
        }                                                                         \
        memcpy(recibido, r->respuesta.dato, payload);                             \
    } while (0)
  1. Escribir el estímulo en la ranura de petición.
  2. Subir el contador (++n) con release. Es el «timbre» que ve el servidor.
  3. Esperar la respuesta: gira hasta que respuesta.seq valga exactamente n. Si nunca llega, tras LIMITE_SPIN giros se rinde en ese intercambio y lo anota en giros_perdidos.
  4. Copiar la respuesta a un buffer local.

Es una macro y no una función para que su cuerpo se expanda en cada uso (estímulo suelto, autoprueba, warmup, medición y lotes) sin el costo de una llamada. El envoltorio do { ... } while (0) es la forma habitual de que una macro de varias sentencias se comporte como una sola.

La medición (líneas 250–267)

for (uint64_t i = 0; i < iters; i++) {
    const unsigned char *est = ciclo[i & 15];
    uint64_t t0 = ahora_ns();
    INTERCAMBIO(est);
    uint64_t t1 = ahora_ns();
    latencias[i] = t1 - t0;

    uint32_t eco;
    memcpy(&eco, recibido + OFF_ECO_ID, sizeof eco);
    if (eco != g_tabla_id[i & 15]) desajustes++;
}
  • Solo lo que está entre t0 y t1 se cronometra: el intercambio completo, ida y vuelta. Es la frontera de medición definida para todas las variantes.
  • ciclo[i & 15] recorre los 16 estímulos en orden. Como 16 es potencia de 2, & 15 equivale a «resto de dividir entre 16» sin hacer una división.
  • La verificación del eco va después de t1, para que comprobar la respuesta no se sume a la latencia. Si las barreras de memoria estuvieran mal, la respuesta llegaría con un eco distinto y desajustes lo delataría.

Los demás bloques importantes

  • Array de latencias preasignado y «tocado» (124–132). malloc reserva memoria virtual, pero el sistema operativo solo la entrega cuando se escribe por primera vez, con un fallo de página (una entrada al kernel). Para que eso no ocurra dentro de la medición, el cliente escribe ceros en todo el array antes de empezar.
  • Piso de medición (134–155). Toma 100 000 pares de lecturas del reloj seguidas, sin nada en medio, y las ordena. Imprime el mínimo, la mediana y el percentil 99 de esa diferencia: es lo que cuesta el instrumento solo. A las escalas de esta variante (decenas de nanosegundos) ese costo es comparable a lo que se mide, y por eso se informa. El mensaje siguiente sobre la granularidad del contador (41,67 ns, de 24 MHz) describe el equipo de referencia; en otra plataforma, la granularidad se lee en el piso medido.
  • Autoprueba (217–231). Envía los 16 hosts de la tabla y comprueba dos cosas en cada uno: que el eco coincida y que el veredicto sea el que dice la tabla. Después envía un host que no está en la tabla (203.0.113.77, del rango reservado para documentación) y exige la respuesta «desconocido». Si algo falla, el cliente termina con error antes de medir. En modo --sin-clasificar solo se verifica el eco. No corre en modo --clasificar.
  • Contraste por lotes (277–308). Repite el intercambio en bloques de 1000 y cronometra cada bloque completo con un solo par de lecturas del reloj; el costo por intercambio es el tiempo del bloque dividido entre 1000. Repite 200 veces, ordena y muestra el mínimo, la mediana y el máximo. Como el reloj tiene un tic grueso (decenas de nanosegundos), esta media por lote da una precisión muy por debajo del tic. No reemplaza a los percentiles (un promedio no tiene cola); sirve de comprobación cruzada: si difiere mucho de la mediana por muestra, alguna de las dos mediciones está mal.

LíneasQué hace
1–9Comentario: se usa -O2 y no -O3 porque -O3 activa transformaciones agresivas cuyo efecto sobre un bucle dominado por la latencia de caché es impredecible y haría el resultado más difícil de explicar (la medición tiene que ser defendible, no máxima); y por qué hace falta -D_GNU_SOURCE en Linux/WSL2 (no cambia el nivel de optimización, ver más abajo).
10–12Variables CC (el compilador, cc), CFLAGS y LDFLAGS. El operador ?= permite reemplazarlas desde la línea de comandos.
14El objetivo por defecto, all: construye server y client.
16–20Cómo se construye cada programa a partir de su .c. Las dependencias incluyen los tres encabezados —common.h, ../clasificador.h y ../reloj.h—: si cambia cualquiera de los tres, se recompila. Declarar ../reloj.h explícitamente es necesario porque make no sigue includes transitivos por su cuenta: aunque common.h lo incluye, hay que decírselo aparte.
22–25clean borra los binarios; .PHONY indica que all y clean son acciones y no archivos.

Las opciones de compilación son:

  • -std=c11: el estándar del lenguaje C, que es el que incluye los tipos atómicos (_Atomic).
  • -O2: optimización moderada.
  • -Wall -Wextra -pedantic: activan los avisos del compilador.
  • -D_GNU_SOURCE: expone en Linux las funciones POSIX de la biblioteca C (clock_gettime, ftruncate, usleep) que -std=c11 estricto oculta. Sin este flag, esta carpeta no compila en Linux ni WSL2 — comprobado.

8. Cómo se ejecuta

A mano, desde sistema/memoria-compartida-c/:

make                                                    # compila server y client
./server --tabla ../tabla-hosts.csv &                   # arranca el servidor en segundo plano
./client --tabla ../tabla-hosts.csv --out /tmp/d.csv    # mide y escribe el CSV
kill %1                                                 # detiene el servidor

Un estímulo suelto, con el servidor ya corriendo:

./client --tabla ../tabla-hosts.csv --clasificar 10.20.0.11
# ESTIMULO veredicto=1 latencia_ns=1900

Con el harness oficial, desde sistema/:

./run.sh memoria-compartida-c 1                    # una ronda completa (1 000 000 de iteraciones)
./run.sh memoria-compartida-c 1 --iters 100000     # una corrida corta de prueba

run.sh hace, en orden: registrar en un .log el equipo donde corre; compilar con make; lanzar el servidor en segundo plano con la tabla; ejecutar el cliente con la tabla y el CSV de salida; detener el servidor; y llamar a analyze.py para calcular los percentiles. Antes de empezar archiva, con su fecha, los resultados de una corrida anterior con el mismo nombre.

Desde la interfaz web, el plano de control (app/servidor.py) usa este mismo cliente de dos formas: al pedir una medición completa, lo lanza con --out y lee el CSV para calcular los percentiles; al mandar un estímulo suelto desde «Probar clasificación», lo lanza con --clasificar <ip> y lee la línea ESTIMULO ... de su salida.

9. Glosario

TérminoQué significa aquí
Memoria compartidaUna zona de memoria que dos procesos proyectan en su propio espacio de direcciones: lo que uno escribe, el otro lo lee directamente. Se crea con shm_open y se proyecta con mmap.
Región / ranuraLa región es toda la zona compartida (256 B). Cada ranura es la mitad que usa un solo sentido de comunicación (128 B).
Línea de cachéEl bloque mínimo que la CPU mueve entre su memoria rápida y la memoria principal; en Apple Silicon son 128 bytes. Dos datos en la misma línea se mueven juntos.
False sharingCuando dos núcleos escriben datos distintos que caen en la misma línea de caché y se obligan mutuamente a descartar su copia. Encarece cada acceso.
AtómicoUna operación que se ve completa o no se ve: nadie observa un valor a medias.
acquire / releaseReglas de orden entre accesos a memoria. release: todo lo escrito antes queda visible antes de esta escritura. acquire: lo leído después ve todo lo publicado antes por el release correspondiente. Juntas garantizan que el mensaje esté completo cuando se ve la señal.
Espera activa (spin)Esperar repitiendo una lectura en un bucle, sin dormirse. Reacciona en nanosegundos, pero mantiene un núcleo al 100 %.
Planificador (scheduler)La parte del sistema operativo que decide qué proceso corre en qué núcleo y cuándo. Dormir y despertar procesos pasa por él, y eso cuesta microsegundos.
Llamada al sistemaUna petición de un programa al kernel (por ejemplo, enviar por un socket). Cruzar al kernel cuesta tiempo y es lo que la memoria compartida evita en el intercambio.
EcoEl identificador del host que el servidor copia de vuelta en la respuesta, para que el cliente compruebe que la respuesta corresponde a su petición.
WarmupIntercambios de calentamiento que se descartan, para que cachés, frecuencia de CPU y rutas de código se estabilicen antes de medir. No aplica al estímulo suelto.
Estímulo sueltoUn solo intercambio, lanzado con --clasificar, sin CSV ni corrida: responde una pregunta y sale. Lo usa la web para «Probar clasificación».
Cuantización / ticEl reloj solo avanza a saltos de un tamaño mínimo (el tic); por eso las latencias medidas caen en múltiplos de ese valor.
Percentil (p50, p99.9)El valor bajo el cual queda esa fracción de las muestras. p50 es la mediana; p99.9 deja fuera solo al 0,1 % más lento.
QoSClase de calidad de servicio de macOS: una sugerencia al planificador sobre cuán urgente es un hilo.
Señal (SIGINT, SIGTERM)Un aviso que el sistema operativo envía a un proceso: SIGINT es Ctrl-C y SIGTERM es la petición estándar de terminar.
csel / cmovInstrucciones de la CPU que eligen entre dos valores sin hacer un salto. Permiten que el clasificador cueste lo mismo para cualquier host.
